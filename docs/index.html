Overview

bbaccounts implements the OAuth 2.0 authorization code grant with PKCE. It issues opaque Bearer tokens rather than JWTs; validate them by calling the user info endpoint. Every credential is scoped to one project.

Do I need my own authorization server? No. bbaccounts is the authorization server. Your app redirects users to bbaccounts, receives an authorization code, and exchanges it for tokens on your backend.

EndpointMethodPurpose
/oauth/authorizeGETStart authorization, render sign-in or consent
/oauth/authorizePOSTSubmit the consent decision
/oauth/tokenPOSTExchange a code or refresh token
/oauth/userinfoGET, POSTRead the authorized profile
/oauth/revokePOSTRevoke an access or refresh token
/api/guardGETRead the Guard secret and current code

All production URLs use https://. The base URL for this instance is https://bbaccounts.unaux.com.

Direct requests

Client secret is NOT an access token

Do not pass client_secret as Authorization: Bearer or ?access_token=. The client secret is used only when exchanging an authorization code for tokens.

How to get an access token

  1. Create a project in Developer, set Redirect URI/scopes, and create a credential. Save client_id and client_secret (confidential clients).
  2. Redirect the user to GET /oauth/authorize?response_type=code&client_id=...&redirect_uri=...&scope=profile%20email&state=...&code_challenge=...&code_challenge_method=S256.
  3. After redirect, exchange code on your server: POST /oauth/token with grant_type=authorization_code, code, redirect_uri, client_id, code_verifier, and client_secret for confidential clients.
  4. The response contains access_token (~1 hour) and refresh_token. Use the token: Authorization: Bearer <access_token> or ?access_token=...

Once you have an access token, every endpoint is a plain HTTPS call to the hosted domain. No SDK is needed. The token identifies the account; you do not pass an account ID separately for token-based endpoints.

You can send the token in three ways (all supported):

# 1) Authorization header (recommended)
curl -i "https://bbaccounts.unaux.com/oauth/userinfo" \
  -H "Authorization: Bearer ACCESS_TOKEN"

# 2) Query parameter
curl -i "https://bbaccounts.unaux.com/oauth/userinfo?access_token=ACCESS_TOKEN"

# 3) token= query parameter (alias)
curl -i "https://bbaccounts.unaux.com/api/profile?username=timinside"

On shared hosting, some proxies strip the Authorization header. If you get invalid_token with a valid token, retry with ?access_token=... or ?token=.... Also send a User-Agent header; some hosts return an anti-bot challenge page to requests without one.

unaux.com / ProFreeHost limitation: this host may show a JavaScript anti-bot challenge (aes.js, sets a __test cookie) before PHP runs. Plain curl cannot execute that JavaScript, so the request may never reach the bbaccounts API. Easy workaround: use the Python stdlib script below (examples/python/bb-unaux.py, no pip) to solve the challenge automatically, or reuse a browser __test cookie in curl. This is a hosting limitation, not an API token problem.

Workarounds for curl:

# 1) Reuse the __test cookie from your browser (works until the cookie expires/IP changes).
#    Open https://bbaccounts.unaux.com/ in a browser, pass the challenge, then copy the __test cookie
#    value from DevTools -> Application/Storage -> Cookies.
curl -i -A "Mozilla/5.0" \
  -H "Cookie: __test=PASTE_COOKIE_VALUE_HERE" \
  "https://bbaccounts.unaux.com/oauth/userinfo?access_token=ACCESS_TOKEN"

# 2) Save/reuse cookies with a cookie jar (useful after you have a valid __test cookie).
curl -i -A "Mozilla/5.0" -c bb-cookies.txt -b bb-cookies.txt \
  -H "Cookie: __test=PASTE_COOKIE_VALUE_HERE" \
  "https://bbaccounts.unaux.com/api/profile?username=timinside"

# 3) POST example with browser-like headers + __test cookie.
curl -i -A "Mozilla/5.0" \
  -H "Cookie: __test=PASTE_COOKIE_VALUE_HERE" \
  -H "Content-Type: application/json" \
  -X POST "https://bbaccounts.unaux.com/api/points?access_token=ACCESS_TOKEN" \
  -d '{"amount":10}'

Python (no pip, stdlib only) - solves the challenge automatically:

Download bb-unaux.py v1.0

Save the file and run it with Python 3. No pip dependencies. Also available as examples/python/bb-unaux.py in the repo.

# Linux / macOS
python3 bb-unaux.py "https://bbaccounts.unaux.com/api/profile?username=timinside"
python3 bb-unaux.py "https://bbaccounts.unaux.com/api/points?access_token=ACCESS_TOKEN" POST '{"amount":10}'

# Windows cmd
python bb-unaux.py "https://bbaccounts.unaux.com/api/profile?username=timinside"
python bb-unaux.py "https://bbaccounts.unaux.com/api/points?access_token=ACCESS_TOKEN" POST "{\"amount\":10}"

For reliable server-side access, disable the challenge for /api/* and /oauth/* in the hosting panel if available, or put a domain/proxy in front that forwards requests directly to PHP. Browser-based user flows are not affected.

# Normal examples (work when no anti-bot challenge is in front of PHP)
curl -i -A "MyApp/1.0" "https://bbaccounts.unaux.com/oauth/userinfo?access_token=ACCESS_TOKEN"

# POST with JSON body and Authorization header
curl -i -A "MyApp/1.0" -X POST "https://bbaccounts.unaux.com/api/points" \
  -H "Authorization: Bearer ACCESS_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"amount":10}'

# POST with token in query
curl -i -A "MyApp/1.0" -X POST "https://bbaccounts.unaux.com/api/points?access_token=ACCESS_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"amount":-5}'

/oauth/userinfo uses the scopes you approved. The /api/* endpoints need the matching verified-project scope: profile, points, friends, badges or teams. A missing scope returns insufficient_scope.

Guard API

The guard scope lets a verified companion app read the account's TOTP secret and current code, so it can show a rotating code locally. Enable Guard under Account → Security first.

GET https://bbaccounts.unaux.com/api/guard
Authorization: Bearer ACCESS_TOKEN

The response contains enabled, secret, code, digits, period and expires_in. Enter the displayed code in the sign-in form to confirm a login; each code is accepted once.

On the same computer, running bbaccounts --service lets the sign-in page ask the desktop window for approval instead. Set guard.service_url to http://localhost:53683/confirm in config.local.php; leave it empty on a hosted install. The page posts {"email","app","ip","user_agent"} and expects {"approved":true}. Denial or an unreachable service falls back to the code field.

Authorization flow

  1. Your app creates a PKCE verifier and sends the user to the authorization endpoint with its S256 challenge and a state value.
  2. bbaccounts signs the user in if needed, then shows the consent screen unless a matching consent already exists.
  3. On approval, the browser returns to your registered redirect URI with a one-time code and your unchanged state.
  4. Your server exchanges the code and verifier for an access token and a refresh token.
  5. Call /oauth/userinfo with the access token. Refresh before the hour is up.

Authorization codes live for 10 minutes and can be used once. Access tokens live for one hour. Refresh tokens live for 30 days and rotate on every use.

Authorization request

Send the browser to this endpoint as a top-level navigation:

GET https://bbaccounts.unaux.com/oauth/authorize
  ?client_id=YOUR_CLIENT_ID
  &redirect_uri=https%3A%2F%2Fapp.example.com%2Fcallback
  &response_type=code
  &scope=profile%20email
  &state=RANDOM_NONCE
  &code_challenge=BASE64URL_SHA256_OF_VERIFIER
  &code_challenge_method=S256
ParameterRequiredNotes
client_idyesA credential client ID from the project page
redirect_uriyesMust exactly match a registered URI
response_typeyesOnly code is supported
scopenoprofile email is the default
staterecommendedReturned unchanged; compare it to your stored value
code_challengerecommended43-128 characters after base64url encoding. Required for public clients
code_challenge_methodnoS256 by default; plain accepted with a 43+ character challenge
promptnoconsent forces the consent screen again

Denial or a bad request redirects back with error and error_description. If the client ID or redirect URI itself is wrong, bbaccounts shows an error page instead of redirecting, because the destination cannot be trusted.

Token exchange

Exchange the code from a server-side request. Authenticate with HTTP Basic or send the credentials in the body.

POST https://bbaccounts.unaux.com/oauth/token
Content-Type: application/x-www-form-urlencoded

grant_type=authorization_code
&code=RETURNED_CODE
&redirect_uri=https%3A%2F%2Fapp.example.com%2Fcallback
&client_id=YOUR_CLIENT_ID
&client_secret=YOUR_CLIENT_SECRET
&code_verifier=YOUR_PKCE_VERIFIER

Response:

{
  "access_token": "…",
  "token_type": "Bearer",
  "expires_in": 3600,
  "refresh_token": "…",
  "scope": "profile email"
}

The request must repeat the same redirect_uri used during authorization. If the code was issued with a challenge, the verifier is mandatory. A public client may omit the secret only when PKCE was used.

User info

Returns the account that owns the access token. You do not pass a username or account ID here; the token already identifies the account. 

# Recommended: Authorization header
curl -i -A "MyApp/1.0" "https://bbaccounts.unaux.com/oauth/userinfo" \
  -H "Authorization: Bearer ACCESS_TOKEN"

# Also works: token in URL
curl -i -A "MyApp/1.0" "https://bbaccounts.unaux.com/oauth/userinfo?access_token=ACCESS_TOKEN"

# Also works: POST
curl -i -A "MyApp/1.0" -X POST "https://bbaccounts.unaux.com/oauth/userinfo" \
  -H "Authorization: Bearer ACCESS_TOKEN"

Fields depend on the granted scopes:

{
  "sub": "42",
  "display_name": "Example User",
  "username": "example_user",
  "description": "Builds small tools.",
  "avatar_url": "https://bbaccounts.unaux.com/avatar/42.svg",
  "email": "user@example.com",
  "email_verified": false,
  "social": { "github": "octocat" },
  "updated_at": "2026-11-09T12:00:00+00:00"
}

sub is the stable account ID. Store it as the external identifier; email addresses can change. email_verified is always false on this instance because there is no email delivery.

social maps each linked provider to its username. The master switch is Profile → Privacy, and each provider is opted in separately under Account → Connections.

Refresh

POST https://bbaccounts.unaux.com/oauth/token
Content-Type: application/x-www-form-urlencoded

grant_type=refresh_token
&refresh_token=CURRENT_REFRESH_TOKEN
&client_id=YOUR_CLIENT_ID
&client_secret=YOUR_CLIENT_SECRET

The response has the same shape as the code exchange. Both tokens are replaced: save the new refresh token, because the old one stops working. A failed refresh means the user must authorize again.

Revoke

POST https://bbaccounts.unaux.com/oauth/revoke
Content-Type: application/x-www-form-urlencoded

token=ACCESS_OR_REFRESH_TOKEN
&client_id=YOUR_CLIENT_ID
&client_secret=YOUR_CLIENT_SECRET

Revoking an access token or its refresh token invalidates the pair. Users can also revoke a whole project from their authorized apps page, which removes consent, tokens, and unused codes at once.

Desktop and native apps

Desktop, CLI, and single-page apps cannot keep a client secret. Create a credential with Public client enabled, use PKCE with S256, and omit client_secret when exchanging the code and refreshing tokens.

Open the authorization page in the system browser, not an embedded web view. Listen on a loopback address and register that exact URI on the project. A fixed port keeps the exact match simple; the example below uses http://localhost:53682/callback.

POST https://bbaccounts.unaux.com/oauth/token
Content-Type: application/x-www-form-urlencoded

grant_type=authorization_code
&code=RETURNED_CODE
&redirect_uri=http%3A%2F%2Flocalhost%3A53682%2Fcallback
&client_id=PUBLIC_CLIENT_ID
&code_verifier=YOUR_PKCE_VERIFIER

Store access and refresh tokens in the OS credential store: DPAPI or Credential Manager on Windows, Secret Service on Linux. The sample at examples/desktop is a Windows-only WinForms net10.0-windows app using HttpListener and DPAPI. The examples/php-web and examples/python folders contain minimal web examples with no dependencies.

Points API

Read or change the point balance of the account that owns the token. The token identifies the account; no account ID is needed. Requires a verified project and the points scope.

# Read balance
curl -i -A "MyApp/1.0" "https://bbaccounts.unaux.com/api/points" \
  -H "Authorization: Bearer ACCESS_TOKEN"

# Add 10 points
curl -i -A "MyApp/1.0" -X POST "https://bbaccounts.unaux.com/api/points" \
  -H "Authorization: Bearer ACCESS_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"amount":10}'

# Spend 5 points (token in URL also works)
curl -i -A "MyApp/1.0" -X POST "https://bbaccounts.unaux.com/api/points?access_token=ACCESS_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"amount":-5}'

Response: {"points": 42}. Amount must be a non-zero whole number between −10,000 and 10,000. The balance never goes below zero.

Friends API

Manage the friend list of the token owner. The token identifies the account. Requires a verified project and friends scope.

# List friends
curl -i -A "MyApp/1.0" "https://bbaccounts.unaux.com/api/friends" \
  -H "Authorization: Bearer ACCESS_TOKEN"

# Send friend request by username
curl -i -A "MyApp/1.0" -X POST "https://bbaccounts.unaux.com/api/friends" \
  -H "Authorization: Bearer ACCESS_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"username":"timinside"}'

# Remove friend / cancel request (42 is the friend's account ID)
curl -i -A "MyApp/1.0" -X POST "https://bbaccounts.unaux.com/api/friends/42/remove" \
  -H "Authorization: Bearer ACCESS_TOKEN"

GET returns count, limit, friends, incoming, and outgoing. POST /api/friends returns state: sent, pending, accepted, or friends.

Profile API

Read a public profile. Pass username to select the account. Without a token, only public base profile data is returned. With a verified project token (profile scope), the token identifies who is asking; omit username to read the token owner's own profile.

# Read a public profile without an access token
curl -i -A "MyApp/1.0" "https://bbaccounts.unaux.com/api/profile?username=timinside"

# Read your own profile (account identified by token)
curl -i -A "MyApp/1.0" "https://bbaccounts.unaux.com/api/profile" \
  -H "Authorization: Bearer ACCESS_TOKEN"

# Read another account with token (friend/self can see full private fields)
curl -i -A "MyApp/1.0" "https://bbaccounts.unaux.com/api/profile?username=timinside" \
  -H "Authorization: Bearer ACCESS_TOKEN"

Private profiles return only avatar, banner, background, display name and username; other fields are none unless the viewer is the owner or an accepted friend. Unknown accounts return 404.

Badges API

Create and issue badges for your verified project. Requires badges scope. Badges are created on the project settings page or through this API. Each badge has a numeric id - use that ID to issue it.

# List project badges
curl -i -A "MyApp/1.0" "https://bbaccounts.unaux.com/api/badges" \
  -H "Authorization: Bearer ACCESS_TOKEN"

# Create a badge
curl -i -A "MyApp/1.0" -X POST "https://bbaccounts.unaux.com/api/badges" \
  -H "Authorization: Bearer ACCESS_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"name":"Beta Tester","description":"Tested the beta"}'

# Issue badge by badge ID to a user by username
curl -i -A "MyApp/1.0" -X POST "https://bbaccounts.unaux.com/api/badges/12/issue" \
  -H "Authorization: Bearer ACCESS_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"username":"timinside"}'

Issuing a badge again is safe. A project can only issue its own badges. The issue endpoint accepts the badge ID in the URL.

Cells API

Store small project data in cells. Requires a verified project and cells scope. Each cell has a numeric id, a key, and a value up to 256KB. A cell can be project-scoped or bound to a user (username).

EndpointMethodPurpose
/api/cellsGETList cells (filter by username, key, scope=project)
/api/cellsPOSTCreate or update a cell by key (upsert)
/api/cells/{id}GETRead a cell including its value
/api/cells/{id}PUT/POSTUpdate cell value
/api/cells/{id}DELETEDelete a cell
 
# Create/update a project-scoped cell
curl -i -A "MyApp/1.0" -X POST "https://bbaccounts.unaux.com/api/cells" \
  -H "Authorization: Bearer ACCESS_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"key":"welcome_message","value":"Hello!"}'

# Create/update a user-bound cell
curl -i -A "MyApp/1.0" -X POST "https://bbaccounts.unaux.com/api/cells" \
  -H "Authorization: Bearer ACCESS_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"key":"save_slot_1","value":"{\"level\":3}","username":"timinside"}'

# List cells for a user
curl -i -A "MyApp/1.0" "https://bbaccounts.unaux.com/api/cells?username=timinside" \
  -H "Authorization: Bearer ACCESS_TOKEN"

# Read / update / delete by cell ID
curl -i -A "MyApp/1.0" "https://bbaccounts.unaux.com/api/cells/42" -H "Authorization: Bearer ACCESS_TOKEN"
curl -i -A "MyApp/1.0" -X PUT "https://bbaccounts.unaux.com/api/cells/42" \
  -H "Authorization: Bearer ACCESS_TOKEN" -H "Content-Type: application/json" \
  -d '{"value":"new value"}'
curl -i -A "MyApp/1.0" -X DELETE "https://bbaccounts.unaux.com/api/cells/42" \
  -H "Authorization: Bearer ACCESS_TOKEN"

List responses omit value; fetch a cell by ID to read its value. Project-bound and user-bound cells with the same key are different cells.

Teams API

Read the token owner's teams. Requires a verified project and teams scope. The token identifies the account.

curl -i -A "MyApp/1.0" "https://bbaccounts.unaux.com/api/teams" \
  -H "Authorization: Bearer ACCESS_TOKEN"

# Token in URL also works
curl -i -A "MyApp/1.0" "https://bbaccounts.unaux.com/api/teams?access_token=ACCESS_TOKEN"

Returns count and teams. Each team includes id, name, slug, your role, subscribed, and members.

Projects and keys

What the Projects tab is for

The Developer → Projects tab is where you set up and manage apps that use bbaccounts OAuth/API.

  • Create a project - register your app/game/service that will sign users in with bbaccounts.
  • Redirect URIs - add exact callback URLs where bbaccounts can return users after authorization.
  • Client credentials - create labeled keys; get client_id and a one-time client_secret for OAuth token exchange.
  • Branding/settings - edit project name, description, logo, and other project details shown to users.
  • Manage access - revoke a key, rotate credentials, or delete a project when it is no longer needed.

Developer access is enabled manually on an account. Once enabled, the developer page lets you create projects, edit branding, register redirect URIs, and issue labeled client credentials. A project can hold up to ten active credentials, so you can rotate one without breaking another integration.

A regular credential gets a secret shown once at creation; if it is lost, revoke that key and create a new one. A public client has no secret at all and must use PKCE. Use public clients for desktop apps, CLIs, and browser-only apps. Deleting a project cascades to its redirect URIs, credentials, authorization codes, tokens, and user consents.

Accounts and recovery

Accounts use email and password. Because this instance cannot send email, there is no verification link and no reset email. Each account receives ten single-use recovery codes at registration; they can be regenerated from the security page with the current password. A code resets the password and is consumed on use.

Changing a password signs out every other session. Sessions last 30 days and slide forward while active. Users can inspect and revoke devices from the security page, and switch between accounts already signed in on the same device without a password. Each account can publish a public profile at /u/{username} with a unique @username, a short description, roles, selected social providers, and up to three showcases: custom text, active projects, Badge Earned, media uploads, GitHub repositories, links, Friends, or Best friends. Badge Earned and Friends are always present and can only be turned off, never removed. Media is an image or video upload and costs 20 points each time; removing it does not refund the points. Earned badges appear only inside the Badge Earned showcase, as artwork with the name shown on hover. Writing @username in a description or showcase links to that profile.

Other signed-in people can like a profile once. A like is worth 2 points to the profile owner, and each accepted friendship earns 5 points for both people. 15 points buy one extra showcase slot (up to ten) or 15 points buy 10 extra friend slots (up to thirty; the base limit is twenty). Rules are published at /rules; blocks, rate limits, unique identities, and self-like prevention are enforced without an administrator online.

Social sign-in

Google, GitHub, and Discord sign-in appear on the login page when the instance has credentials for them in private/config/config.php. Each provider links only to an existing account when its verified email matches. Social sign-in never creates an account: register with email first, then connect the provider.

Linked providers do not replace your password. Set one in Security if you signed up with email and password. A provider cannot be disconnected if it is the only way to sign in.

Provider setup lives in the main README: create the OAuth app, set the callback to https://bbaccounts.unaux.com/oauth/social/google/callback, https://bbaccounts.unaux.com/oauth/social/github/callback, https://bbaccounts.unaux.com/oauth/social/discord/callback, https://bbaccounts.unaux.com/oauth/social/yandex/callback, or https://bbaccounts.unaux.com/oauth/social/apple/callback, and fill in the required credentials. See OAUTH-SETUP.md for each provider. Apple requires a Service ID, Team ID, Key ID, and private key. Steam is not a sign-in provider: link a Steam ID from your profile contacts instead.

Examples

Real step-by-step flows. Each example links to the API section that explains the details.

1. Sign in with bbaccounts (OAuth login)

Use this when your app needs to identify a user. Needs a project in Projects and keys.

  1. Create project credentials. In Developer → Projects, create a project, add your Redirect URI, and create a credential. Save client_id and client_secret. See Projects and keys.
  2. Send user to bbaccounts. Redirect the browser to Authorization request: 
    GET https://bbaccounts.unaux.com/oauth/authorize?response_type=code
  &client_id=YOUR_CLIENT_ID
  &redirect_uri=https://your-app.example/callback
  &scope=profile%20email
  &state=RANDOM_STATE
  &code_challenge=BASE64URL_SHA256_VERIFIER
  &code_challenge_method=S256
  3. User approves access. bbaccounts redirects back to your redirect_uri with ?code=...&state=....
  4. Exchange code for tokens on your server. See Token exchange: 
    curl -X POST "https://bbaccounts.unaux.com/oauth/token" \
  -H "Content-Type: application/x-www-form-urlencoded" \
  -d "grant_type=authorization_code" \
  -d "code=CODE_FROM_CALLBACK" \
  -d "redirect_uri=https://your-app.example/callback" \
  -d "client_id=YOUR_CLIENT_ID" \
  -d "client_secret=YOUR_CLIENT_SECRET" \
  -d "code_verifier=ORIGINAL_VERIFIER"
  5. Read user profile. Use the returned access_token with User info: 
    curl "https://bbaccounts.unaux.com/oauth/userinfo" \
  -H "Authorization: Bearer ACCESS_TOKEN"

2. Get public profile data (no access token)

Use this when you only need public profile info by username. No OAuth flow needed. See Profile API.

curl -i -A "MyApp/1.0" "https://bbaccounts.unaux.com/api/profile?username=timinside"

Private profiles return only base fields; other fields are none.

3. Get my own profile (with access token)

Use this when your app has a user token and needs the token owner's own profile. See Profile API.

curl -i -A "MyApp/1.0" "https://bbaccounts.unaux.com/api/profile" \
  -H "Authorization: Bearer ACCESS_TOKEN"

4. Issue a badge to a user

Use this when your verified project wants to reward a user. Needs badges scope. See Badges API.

  1. Create a badge. On the project settings page, open Badges and create one. Note its numeric ID (shown in the badge list).
  2. Issue it by badge ID. 
    curl -i -A "MyApp/1.0" -X POST "https://bbaccounts.unaux.com/api/badges/12/issue" \
  -H "Authorization: Bearer ACCESS_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"username":"timinside"}'
  3. Check result. The response includes badge_id, username, and slug. Issuing again is safe.

5. Save user data in a storage cell

Use this when your verified project needs to store small per-user or per-project data (up to 256KB per cell). Needs cells scope. See Cells API.

  1. Create or update a cell. Send key, value, and optional username to bind it to a user: 
    curl -i -A "MyApp/1.0" -X POST "https://bbaccounts.unaux.com/api/cells" \
  -H "Authorization: Bearer ACCESS_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"key":"save_slot_1","value":"{\"level\":3}","username":"timinside"}'
  2. Read it later. List by username/key or fetch by cell ID: 
    curl -i -A "MyApp/1.0" "https://bbaccounts.unaux.com/api/cells?username=timinside&key=save_slot_1" \
  -H "Authorization: Bearer ACCESS_TOKEN"

Explain it like I am new

Think of bbaccounts as a "Sign in" button owner.

  1. Your app does not store the user password. When someone wants to sign in, your app sends them to bbaccounts.
  2. The user signs in on bbaccounts and clicks Allow. bbaccounts sends the user back to your app with a temporary code.
  3. Your server exchanges that code for an access token. The code is like a one-time ticket; the access token is like a temporary pass.
  4. Your server uses the access token to ask bbaccounts who the user is. Then your app creates its own session/cookie for that user.

Important: client_secret is a password for your app server. access_token is a temporary pass for a user. Never mix them up.

If you only need public profile info by username, use GET /api/profile?username=... — it does not need an access token.
